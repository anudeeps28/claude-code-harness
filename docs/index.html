why it exists

AI coding tools are powerful. Unstructured.

No plan to review.You start a task, the model edits twelve files, and you're not sure what happened or why.
No evaluation to catch mistakes.Nothing checks whether the change actually matches what was asked for.
No proof for your team.Management doesn't trust AI-generated code because nobody can show a human approved the plan before code was written.

The harness adds the structure

Every feature runs through human gates — understand, goal, plan, execute, evaluate, PR — and nothing advances without your explicit "go".

For teams it goes further: tracker integration, PR review loops that drive threads to zero, sprint files, and handoff contracts that leave an audit trail per story.

how a run works — /implement, solo

Six phases. Gated end to end.

1

Understand

Reads the GitHub issue (or a plain-text description), maps the relevant source files, and writes a brief. Flags let you widen the front end first.

flags: --discuss (pre-plan Q&A) · --research (codebase reuse scan) · --quick (skip evaluation) · --auto (run all waves) · --full (= --discuss + --research)

1.5

Goal definition

Locks the acceptance bar — the definition of done — before a line of code is written. The run treats this as mandatory and never skips it.

■ STOP 1.5 — approve the goal before any building starts.
2

Plan

Produces an XML task plan — tasks grouped into waves — and a test strategy in one pass.

■ STOP 1 — review the plan. say go to start building.
3

Execute, wave by wave

Each task runs in an isolated git worktree. Every verify step runs build + relevant tests — a task is only ✓ when tests pass. Three failures on anything stops the retries and auto-invokes /debug for root-cause diagnosis.

■ GATE — after every wave: continue?
3.5

Local verification

Runs /local-test to confirm the full build and test suite pass. Stack-agnostic — it reads your commands from the task files.

4

Evaluate + accept + PR

Four review agents run in parallel — an adversarial evaluator, an acceptance tester, an architecture reviewer, and a security reviewer. Then commit messages and a PR description are drafted.

■ STOP 3 — review and commit. say push when ready.

On teams, /story runs the long version: an eight-phase lifecycle with handoff contracts written to disk at every step — brief.md → plan.md → test-strategy.md → executor-state.md → evaluation.md → acceptance.md (plus architecture-review.md and security-review.md) — so the evaluator can check work against the original plan, and anyone can audit what was approved, when, and by whom.

what's in the box

Install once. Ship faster.

35
Skills

Slash commands from /implement to /improve-harness — each a folder you can read, edit, and extend.

19
Agents

Purpose-built sub-agents: planners, executors, an adversarial evaluator, architecture and security reviewers, PR analysts, debuggers — plus the two role identities a session orchestrator spawns.

5
Hook events

Cross-platform Node hooks across 5 lifecycle events (12 scripts): safety checks on destructive ops, drift detection, session logs, pre-compact state saves.

5
Path-scoped rules

Rules that activate only when matching files are touched — code style, testing, security, docs. Five path-scoped of ten total.

4
Tracker adapters

Azure DevOps, GitHub, Todoist, and a local file-based backend behind one 8-script interface. PR review threads run through a separate 3-script code-platform layer (GitHub, Azure Repos, or none).

0
Databases

File-based state. tasks/ is the source of truth — git-friendly, diff-friendly, human-readable.

Model routing Opus for thinking Sonnet for typing Haiku for data gathering — quality where it matters, cost saved where it doesn't

key design decisions

Opinions, stated up front.

  • ✓Human gates everywherenothing advances without an explicit "go"
  • ✓3-attempt rulethree failures stop the retries and invoke /debug — no infinite loops
  • ✓Adversarial evaluationthe evaluator tries to break the work, not defend it — no self-grading bias
  • ✓File-based stateno database, no external service — just markdown in your repo
  • ✓Worktree isolationevery task builds in its own git worktree, auto-cleaned after
  • ✓Tracker abstractionskills never know if you're on ADO, GitHub, Todoist, or local — and PR review runs through a separate code-platform layer

quick start

Two commands. Five questions.

terminal
git clone https://github.com/anudeeps28/claude-code-harness
node claude-code-harness/install/install.js
# windows, macOS, linux — or install.sh on unix

prerequisites — Claude Code installed · GitHub: gh CLI + gh auth login · ADO: az CLI + azure-devops extension · Todoist: td CLI (or $TODOIST_CLI) · local tracker: no CLI needed

  • Global or per-project?
    ~/.claude/ for every repo, or .claude/ for one.
  • Solo or enterprise?
    Simple issues workflow, or full sprint ceremony.
  • Where should your task list live?
    Local files (default), an external tracker, or both. External is GitHub or Todoist on solo; Azure DevOps, GitHub, or Todoist on enterprise.
  • Where do your pull requests live?
    GitHub / GitHub Enterprise, Azure Repos, or none.
  • Your details.
    Your name and project name — org and team members on the enterprise pack.

Then open Claude Code and type /implement #42. The first gate is minutes away.
