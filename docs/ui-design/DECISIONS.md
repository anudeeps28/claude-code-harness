# Harness app: decisions

Decisions made while planning the harness desktop app. They feed `/plan-features`. Where this file and
`PROMPT.md` / `DATA.md` disagree, this file wins.

The design is **version 2 (final)**, received 2026-11-14; version 1 is kept in `v1/` for the details
version 2's DESIGN.md left out but the prototype still has. See "Design version 2" below.

Answers are also written to the plan and decisions log (kept forever); the file follows the step-file retention | Structured, survives restarts, works for terminal runs | 2026-11-13 |

| 13 | PR watcher | **The worker polls each open PR every 5 min with plain code (no AI)**: checks, new review comments, merged. New comments → it starts a Claude Code run in the feature's worktree that fixes them test-first and pushes, **without asking**; anything that is not a clear fix (a reviewer question, a disagreement) becomes a "Needs you" card. Merged → Merged column, worktree cleaned up, Completed a day later. Open PRs are stored with the feature, so it survives restarts. **GitHub first**; other hosts later as adapters. Borrow logic from the factory's `reference/pr-watch.md` | Polling costs nothing; an AI session waiting for days wastes a slot and dies on restart | 2026-11-13 |
| 14 | Pause, resume, park | **Code-only, at a step boundary.** Pause → the card shows "Pausing · finishing <step> first" at once; the worker watches the run's progress file and, the moment the step-finished line appears, ends the Claude process itself (no AI obeys a message). **"Stop now"** is on the card from the start: ends it immediately, and resume redoes that step. Resume = the worker restarts `/implement --resume <fid>`. Park = pause + free the slot; the feature returns to Up next unnumbered ("Parked by you"), worktree untouched; un-park re-queues it | Nothing half-written; deterministic | 2026-11-13 |
| 15 | Rule: AI works, code keeps the books | **AI does the work and the judgment** (code, fixes, plans, questions). **Code does the bookkeeping**: state changes, timing, starting/stopping, checks. A slot frees → `/implement --resume <fid>` reads the approval from disk and builds. The worker never resumes a feature at the gate without the click. Terminal runs keep today's behaviour (a resume after the gate is the approval) | Approval is a fact on disk, not a message the AI interprets | 2026-11-13 |

## Decision 25 items

Source: factory `work-feature` on Azure DevOps `origin/master` as fetched 2026-11-13 (local `C:\SoftwareFactory` was 30 commits behind; not pulled).

1. **PR fixing, reviewer-agnostic** (from `reference/pr-watch.md`). Each project records its review bot, if any (auto-detected from the first bot comment on its PRs; editable in project settings); one small adapter per known bot knows its "done" signal (CodeRabbit first). No bot, or no clear signal, and for human comments: wait for **quiet** (no new comments for 10 min, setting). Always: fix everything, then **one push**; close every unfixed thread with a short reason ("bot misread X" / "moved to #42"); questions or disagreements become a card; the worker then confirms nothing is left open (#15). No reviews at all: wait for checks and the user's merge. Medium.
2. **Finish on merge** (from `SKILL.md` finalize, `reference/finalize.md`). The worker, on merge: marks the feature and its stories done in the tracker (code); turns stories that did not land into a **follow-up feature** linked to the original, which waits for its own plan approval; removes the worktree only after checking nothing is uncommitted or unpushed, never with force, and tells the user if it can't. Medium.
3. **Up to date with main before the PR** (from `SKILL.md:808-814`). Just before opening the PR: merge latest main into the feature branch (merge, no rebase); resolve clashes; if anything came in, re-run the feature's tests; confirm the branch is 0 behind; then open the PR. A hard clash (two features changed the same thing differently) is not guessed: it becomes a "Needs you" card. Small.
4. **Cross-story criteria review** (from `reference/feature-tests.md:5-12`). One `story-reviewer` run in its existing **Cross-story** mode reads every story's criteria together against the feature's scope and reports duplicates, gaps and criteria nobody could check. Runs once in the final review panel; findings are fixed like any other. Small (the mode exists; `/implement` never calls it).
5. **Builder self-check + neighbour tests** (idea from factory `agents/story-builder.md:74-108`; its 8 items are day-job specific and are NOT copied). Each project keeps a **self-check file, `docs/self-check.md`, committed to git** (one per project, "code in this project always…"), seeded with a short general list (negative case per criterion; bad input gives a clear error, not a crash; comments/docs claim nothing the code doesn't do; tests isolated and order-independent; the test rules hold). The builder checks its own diff against it before handing back and fixes what it finds (reviews still review everything). It grows through the docs step (item 7): a kind of review finding repeated in 2+ stories → a proposed new line, added only on the user's OK. **Neighbour tests** (existing tests next to the change) are named by the builder and run at the end of each story. Small.
6. **Honest PR report + house rules** (from `SKILL.md:692, 831-837`, `reference/preflight.md`). (a) Tests that cannot run on this machine are reported **"did not run"** with the reason, never "passed". (b) **Every project has house rules: `docs/definition-of-done.md`, committed to git and named by the project's `CLAUDE.md`** (what every finished feature includes, e.g. README, changelog, no new warnings, new settings in the example config). New project / install / update drafts a starter list fitted to the project for the user to approve. The builder gets it as a checklist; **before the PR a reviewer walks it line by line**: met (where) / not applicable (why) / outstanding. Small outstanding items are fixed in-run; bigger ones go to "Not done", registered as tracker items per `rules/deferrals.md`. The docs step (item 7) proposes new house rules (something new needs a rule, or a problem repeats across features); added only on the user's OK. (c) The PR body opens with a **"Not done"** section. Medium.
7. **Docs step + one whole-feature rules review + `/branding`** (from `SKILL.md:739-756`, `agents/branch-reviewer.md:85-95`, factory `skills/branding/`).
   - **Lean `CLAUDE.md`**: it only points to `docs/rules.md` (the project's own rules), `docs/branding.md`, `docs/definition-of-done.md` (item 6) and `docs/self-check.md` (item 5), all in git. The docs step edits those files, never `CLAUDE.md` beyond adding a pointer.
   - **Docs step** (before the PR, own commit): updates README / `docs/` / setup instructions to match what was built; proposes new house-rules and self-check lines from this feature's findings (user's OK each); adds a lesson only when no test or rule already catches the trap.
   - **Rules review once per feature**: per-story reviews keep "does it work?" (Correctness); the per-story Rules-and-quality review is replaced by one whole-feature review against `docs/rules.md` and `docs/branding.md`.
   - **Port the factory's `/branding` skill**: reads the existing UI (colours, fonts, styles, components, screens) and grills the user; writes checkable rules, not adjectives; converts an existing brand guide; may include screenshots of current screens. Offered at New project or the first feature that changes something users see, when the project has a UI and no branding file. Projects without a UI are not asked.
   - Medium.
8. **Red tests this feature didn't cause** (from `SKILL.md:547-583`). Before counting a red test as this feature's failure: run it alone (passes → flaky or machine busy); run it on `main` in a scratch copy (fails → already broken); timeout-only failure → re-run alone with a longer limit. Then: caused by this feature → fix as normal; flaky/already broken and small → fix in its own commit; bigger → registered as a tracker item and noted in the PR, never allowed to swallow the feature (`rules/autonomous-mode.md` scope, `rules/deferrals.md`). The step history records each suite's duration. Small.
   - (Items 5 and 6) House rules vs self-check: house rules = what a finished **feature** includes, checked once per feature before the PR; self-check = mistakes the **code** must avoid, checked by the builder every story. Both grow only through the docs step with the user's OK.
9. **Lighter review panel for small changes** (from `reference/review-sweep.md:18-31`). The final panel runs 4 reviews instead of 8 when the whole feature changed **under 300 code lines** and touched **nothing sensitive**. A **script decides, not the AI** (decision 15): it counts changed code lines and matches changed file paths (`auth`, `login`, `permission`, `payment`, `billing`, `secret`, `migration`, …) and changed lines (`password`, `token`, `apiKey`, `DROP TABLE`, …) against a per-project list seeded with a starting set that the user can extend. Any match or 300+ lines → full panel. The script's verdict and reason are saved so the screen can show why a feature got the lighter panel. Small.
10. **Saved proof per acceptance check** (from `reference/prove.md:19-26`). Each check keeps its proof: a screen recording of the app window (Playwright; no webcam or microphone), the request/response for an API, or the test output. Named `AC<n>-story<s>-<kind>.<ext>`, stored in `tasks/features/<fid>/evidence/`, gitignored, never uploaded, deleted on the step-history retention schedule (summary lines kept forever). A **script** confirms every "met" has a non-empty proof file, and a "met" without one doesn't count. A sign-off check shows "signed off by you" instead of a file. Dig deeper shows a player or viewer per check. Medium.
11. **One-pass re-check after panel fixes** (work-feature's shape). After fixing panel findings, one pass checks only those findings and marks each **GONE** or **STILL THERE**; it does not hunt for new ones. If the fix touched anything the item 9 script calls sensitive, the security review re-runs in full (code decides). Replaces re-running the whole panel until clean. Small.
12. **No "if you don't answer, I will…" line** (work-feature's shape not taken): Approve stays disabled until every question is answered (decision 16), so a default would never apply. Instead the plan gate gets an **Accept all recommended** button that fills every unanswered question with its recommended answer; the user still sees each and presses Approve. Design addition B7. Small.
13. **Cross-story check on the plan too** (extends item 4). story-reviewer's Cross-story mode also runs on the plan **before the plan gate** (plan only, no code): duplicates and untestable checks are fixed in the plan; a gap that needs a choice becomes a gate question. It still runs again in the final panel to catch drift. Small.
14. **Push after each story** (taken from work-feature). After each story's commit, push the feature branch (one branch per feature, one commit per story, **no story branches**). Backup only, and `main` is untouched until the PR merges. Never force-push: fixes are new commits and catching up with main is a merge (item 3). Knock-on: the session-start cleanup in `rules/git-worktrees.md` decides "merged" from **the PR being merged on GitHub**, not from the branch being gone from origin; the Feature live check stays. Small.
15. **Stories within a feature stay one at a time** for v1; parallelism is across features (5 slots). Story-level parallel (own folder and branch per independent story, merged back into the feature branch) is revisited only if a single feature proves too slow in real use.
- **Not brought over from work-feature:** proceeding on ambiguity (we ask at the plan gate); dropping the per-story review; auto-merge (the user always merges); PR watching inside the AI session (the worker does it, decision 13); writing tests after the code for coverage (we stay test-first).

## Settled at planning (2026-11-14)

## Open checks

- Decision 5, how the worker starts Claude Code (checked 2026-11-13 against code.claude.com docs):
  - **Recommended: spawn the user's own installed, unmodified `claude` CLI** (`-p`, `stream-json` in and out, `--verbose --include-partial-messages`, `--forward-subagent-text`; resume with `--resume <id>`; never `--bare`). Anthropic's legal page allows an end user to sign in to the unmodified binary with their own subscription. The app must never read, store or proxy their credentials, and never pay for or resell their usage.
  - The Agent SDK may **not** use claude.ai subscription logins in a third-party product without Anthropic's approval: API key or cloud provider only.
  - No email to Anthropic (decided 2026-11-13): the docs allow this route; we follow its conditions (unmodified `claude`, never touch credentials, never charge for Claude usage, no Claude/Anthropic in the product name), re-read the terms before launch, and the adapter also accepts the user's own API key as a fallback.
  - Still to settle while building: the exact stdin message format; reported "Agent SDK credit" billing change (unconfirmed).
  - Naming: the product must not use "Claude Code" or Anthropic names/logos in its name; "runs Claude Code" in plain text is fine.
