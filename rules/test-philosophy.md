# Testing Philosophy

This rule defines the testing philosophy for all code generated by this harness. Every skill and agent must follow these principles.

---

## Core Principle

**A feature is not done until it is tested.** Not "compiles" — tested. A story is done, after its review, when:
1. The code compiles (build passes)
2. Unit tests for the changed code pass
3. The feature works as intended (acceptance criteria met, each with its proof)
4. Existing features still work (regression check)

If any of these fail, the story is not done.

**"Done" is goal-met, not "compiles + tests ran."** A feature is done only when the story's tests pass (build + unit tests green, by its test command) **AND** its acceptance criteria are satisfied **AND** its end-to-end gate is green (machine-green or human-accepted). Planning defines that goal up front — the acceptance criteria and the e2e gate (see Level 3) — and work iterates toward it until it is genuinely met, not until the code merely builds.

---

## Three Levels of Testing

### Level 1 — Unit Tests (per story)

Every code change must have corresponding unit tests. These run as part of the story's test command.

- Test the public interface of the changed code
- Test happy path + key edge cases
- Mock only external boundaries (DB, HTTP, file I/O) — never mock internal classes
- If a story changes a method, there must be a test that exercises that method

**Gate:** The story's test command includes running relevant unit tests. The story is done only when build and unit tests pass and its review has passed.

### Level 2 — Integration Tests (per feature)

After the stories of a feature are built, integration tests verify the components work together.

- Test the feature end-to-end through the actual system (API → service → database, or UI → API → service)
- Use real dependencies where practical (test databases, emulators, in-memory providers)
- Test that the feature interacts correctly with existing components
- Test that existing features are not broken by the new code

**Gate:** Integration tests must pass before the feature can proceed to evaluation/PR.

### Level 3 — Acceptance Tests (per feature)

Verify what the user actually sees and experiences. These are derived from the acceptance criteria defined in the test strategy.

- Each acceptance criterion from the plan becomes a testable scenario
- Test from the user's perspective: "User does X → sees Y"
- Must cover the golden path and critical edge cases

**Acceptance is realized through a modality chosen per feature during planning.** There is no single fixed form. Depending on what the feature does, the end-to-end acceptance check may be:

- an **automated test** (API / integration),
- **UI automation** (driving the running app),
- a **domain-specific graded evaluation** — for non-deterministic / AI output, judged against a ground truth, or
- a **structured human acceptance check** — when no machine oracle exists (the criterion needs a human ruling or a subjective judgement).

**The menu is open.** If a feature needs a verification modality that doesn't exist yet, planning **defines it and adds the building of that probe/harness to a story** — coverage is never dropped because the tooling is missing. Project-specific modalities and tooling are defined in the project's own skills/docs, not in this rule.

**The acceptance criteria and the end-to-end gate are the same unified list**, not two separate ones. Each criterion is written so the gate directly checks it (criterion → check, one thing). Only criteria that genuinely cannot be automated stay as separate structured-human checks.

**No-oracle features are still gated, never skipped.** When there is no machine oracle, the gate becomes a structured human acceptance check: the actual behavior is shown (see *Observability* below) and a human explicitly signs off against the criteria. The gate is satisfied by **machine-green OR human-accepted** — never bypassed.

**Observability is part of the strategy.** For every acceptance criterion, planning records how the actual state will be observed (API response, log line, trace, screenshot, structured query). **If the actual state can't be seen, build a way to see it (a probe) in the story** — respecting the project's data-access rules (e.g. observe via API/logs, not raw production DB reads).

**Gate:** Acceptance criteria must be verified (PASS/FAIL per criterion) before PR — by the feature's chosen modality, machine-green or human-accepted, never skipped. The chosen modality, its concrete gate, and the observability plan are a **planning artifact** (see *Test Strategy Is a Planning Artifact*).

---

## Test Strategy Is a Planning Artifact

Every plan must include a test strategy. This is not optional. The test strategy defines:

1. **Acceptance criteria and their proofs** — What proves the feature works, written as testable scenarios. These ARE the e2e gate (one unified list — see Level 3). Each criterion carries three lines, decided before any code:
   - **Proof** — how it is proven: unit, integration, e2e, UI automation, graded evaluation, or a person's sign-off, plus the exact test or check.
   - **Seen by** — how the real result is seen (API response, log, screenshot, read-only query); if it can't be seen, a probe to build. This is the observability plan, per criterion.
   - **Would lie if** — what would let the proof pass while the criterion is unmet: a named mutation or a missing assertion. A proof nobody can say how to fool has not been thought through.
2. **Chosen e2e modality + concrete gate** — Which modality from the open menu verifies the goal end-to-end, and the exact gate that must go green.
3. **Integration test scenarios** — How the feature interacts with other components
4. **Regression guardrails** — What existing behavior must NOT change
5. **Tests to write first** — The tests each story names in the plan, one per criterion at least

The plan also restates the item's **Demo** — what visibly changes and where you see it — unchanged or more precise, never weaker. A criterion proven by a sign-off keeps its story open (`needs-person`) until a person gives it.

The test strategy — including the goal (acceptance criteria + their proofs + e2e modality/gate) — is produced during planning and verified end-to-end before PR. "Done" is goal-met (see Core Principle).

---

## Every Story Has Its Tests Planned

Every story section of the plan names the tests to write first (**Tests to write first**), one per
acceptance criterion at least. They are real parts of the plan, not afterthoughts:

- At minimum: unit tests for every new/changed public method
- For features touching multiple components: integration tests
- For user-facing features: acceptance test scenarios

Tests are never deferred to "we'll write tests later": they come first, see below.

---

## Test-First Mode (every story, and `--tdd`)

**Every story is test-first**, whether or not `--tdd` was passed (the flag is kept and changes
nothing). The story loop writes the failing test **before** the code: a builder writes the tests from
the criteria alone, the test runner shows them red, and only then does a second builder write the
code. A bug is test-first like any other story, and its first test reproduces the bug: the code already
exists, so the cost is near zero and the failing test is the proof the bug was genuinely reproduced.

### The shape of a story

| | Feature story | Bug fix |
|---|---|---|
| 1 | the tests, from the criteria (plus the smallest stub, when the language needs one to compile) | the test that reproduces the bug |
| 2 | the test runner shows them red; the red is recorded | the test runner shows it red; the red is recorded |
| 3 | the real code — the tests now pass | the fix — the test now passes |

The stub exists because a compiled language will not build a test against a class that does not
exist. Without it the test cannot fail for the right reason — it never runs at all. It is the smallest
signature that lets the test compile, with no logic.

**Each step is its own job, so each gets a fresh agent.** They must never be merged. An agent that
writes both the tests and the code chooses the expected value *and* the answer, and can satisfy its
own test by accident — the code returns an empty string, the test expects an empty string, the test
passes, and the story looks already built when nothing was built.

The agent that writes the real code may **read** the test — it needs to know what it must satisfy —
but may never edit it.

### What counts as a real failing test

Inverting pass and fail is not enough. **A green result can lie**, and so can a red one. The point of
the failing test is not the failure — it is the proof that the test actually exercises the thing about
to be built. A test that cannot fail before the code exists will not fail after the code breaks either.

- **A real failure** is one caused by **the behaviour being absent**, in code the test actually
  reached. Two shapes count: an **assertion failure** (expected X, got Y), or an uncaught
  **`NotImplementedException` from the method under test** — the empty shell was reached and has no
  behaviour yet. The second is the *normal* first red on a feature slice, and the runner reports it as
  an exception with no assertion text at all, so a contract demanding "an assertion failure" would
  reject the textbook correct red every time.
- **A fake failure** says nothing about the feature: a compile break, a crash in setup or fixture
  construction, an exception thrown from somewhere other than the method under test, or a
  dependency/config failure. The line is **where the failure came from**, not whether it was an
  assertion. Broken test — fix and retry.

A test that *passes* by asserting `Assert.Throws<NotImplementedException>(…)` is the opposite case: it
asserts the shell rather than the behaviour, and is a false green.

The rules a test is written by, including every way a green result can mislead and the response to
each, live in `skills/implement/reference/test-rules.md`.

### Fixes found after the build are test-first too

A review finding, a failed acceptance criterion, a red e2e gate — any real defect surfaced *after* the
build — is fixed **test-first**, exactly like a bug fix: write the failing test
that reproduces the defect, watch it fail, then fix it. Two steps, no stub; the code already exists.

This is the point where the discipline is most easily lost and matters most. The whole run has been
test-first, and then at the one moment a genuine defect appears, the temptation is to patch the code
and move on — which produces a fix with no test proving it was ever broken, inside a run that will
report full test-first compliance. If a defect was worth fixing, it was worth a test that fails
without the fix.

The only exception is a defect with nothing to assert against — a doc correction, a comment, a
rename. Same rule as below: state the reason.

### Preserve the evidence that the test was red

Nothing is committed between the red run and the code, so once the implementation lands there is no
trace left that the test ever failed — an honest run and a run that wrote both test and code together
are indistinguishable afterwards. The proof of test-first is the one thing test-first does not persist.

So when the test runner shows the new tests red, the orchestrator records, in the story's
`executor-state.md` under `## Red evidence`, one line per test:

- the test's full name and the criterion it covers
- the runner's **verbatim failure line** from the test runner's report (never the builder's own run)
- which failure shape it was (assertion, a `NotImplementedException` from the method under test, or
  `already-met`: the behaviour already exists, recorded with the existing code as `path:line`, so no
  red can be seen and the test stays as a regression test)

`bin/red-evidence.js check` reads them and rejects a compile error or a test that never ran. It costs
nothing and it is the only surviving evidence that the red was real.

### Which changes go test-first

Only changes to **what the system does**. Renames, config values, doc updates and package bumps
have nothing to write a failing test against, and forcing the cycle on them produces empty ceremony
and meaningless tests.

The planner makes that call and **must write the reason into the plan** whenever it skips a test.
Not a bare "exempt" — a stated why, visible at plan approval. Without that, the cheapest way to satisfy
the mode is to declare everything a non-behaviour change, which turns test-first off while appearing
to comply.

## Test Commands Run Tests

The story's **Commands** must include running the relevant tests, not just building:

- **Wrong:** `dotnet build src/Project.csproj`
- **Right:** `dotnet build src/Project.csproj && dotnet test src/Project.Tests.csproj --filter "RelevantClass"`

The planner writes the story's test command so that it includes test execution. The specific test command syntax comes from `tasks/lessons.md`.

---

## Regression Is Everyone's Job

Every change must be checked for regression:

- Unit tests catch method-level regression
- Integration tests catch component-interaction regression
- The evaluator checks for unintended side effects in the diff
- The acceptance-test-agent verifies existing behavior is preserved

If a test breaks and it's not related to the current feature — that's a regression. Fix it before proceeding, don't skip it.

---

## What "Stack-Agnostic" Means

This philosophy applies to any language, framework, or stack. The specific test commands, frameworks, and conventions are defined in `tasks/lessons.md` — not hardcoded anywhere:

- .NET → xUnit/NUnit, `dotnet test`
- Node.js → Jest/Vitest, `npm test`
- Python → pytest, `python -m pytest`
- Go → `go test ./...`
- Angular/React → Cypress/Playwright for e2e, Jest for unit
- Any other stack → define your commands in `tasks/lessons.md`

The harness reads commands from `lessons.md` and executes them. The principles are universal.
